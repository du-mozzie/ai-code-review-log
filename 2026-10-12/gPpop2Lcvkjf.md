### 3. 其他问题清单

#### 1. 术语一致性缺失（一般问题）
*   **位置**：全文
*   **描述**：文档中交替使用“轨迹”、“Trace”、“Trajectory”、“Transcript”。虽然在不同段落可能有上下文，但作为架构文档，术语必须全局统一。
*   **影响**：增加后续开发人员理解成本，易导致 API 设计混乱。
*   **建议**：建立术语表（Glossary），在文档开头或附录中明确定义核心术语。

#### 2. 缺乏失败模式（Failure Modes）分析（一般问题）
*   **位置**：四.2 “Agent 声称成功，不代表环境中的任务已经完成”
*   **描述**：文档提到了需要核对“环境的最终状态”（Outcome），但未详细列举常见的 Agent 失败模式（如：幻觉工具调用、死循环、部分成功、状态回滚失败等）。
*   **影响**：评测平台可能只覆盖了“成功/失败”二元状态，忽略了“部分成功”或“错误成功”的细微差别，导致评测粒度不够。
*   **建议**：增加“Agent 常见失败模式分类”章节，并在 Rubric 设计时对应这些模式。

#### 3. 成本与性能未量化（可优化项）
*   **位置**：三.1 “效率：耗时、Token 消耗、工具调用次数”
*   **描述**：提到了效率指标，但未给出**基准线**（Baseline）或**SLO**（Service Level Objective）建议。
*   **影响**：开发团队不知道“好”的效率是多少，难以进行性能优化和回归检测。
*   **建议**：提供示例 SLO，如“P95 延迟 < 5s”，“Token 消耗 < 2000 per task”，并说明如何根据业务场景动态调整。

#### 4. 人机协作流程缺乏工具支持描述（一般问题）
*   **位置**：四.3 “Skill 评测要进入开发与发布流程”
*   **描述**：提到了“人工对齐 -> 机评对齐”的流程，但未描述**工具链**如何支持这一过程（如：人工标注界面、分歧处理工作流、版本控制）。
*   **影响**：若缺乏配套工具，人工对齐过程将极其低效，难以规模化。
*   **建议**：简要描述评测平台需提供的**标注工作台**（Labeling Workbench）功能，支持多人协作、分歧高亮、批量审核。

### 4. 改进建议

#### 1. 增加“架构落地参考”章节
*   **现状**：文档偏重于“做什么”（What）和“为什么”（Why），缺少“怎么做”（How）的技术细节。
*   **建议**：增加一节“评测系统架构参考”，包含：
    *   **数据流图**：展示 Task -> Agent Harness -> Trace Storage -> Evaluation Engine -> Dashboard 的数据流向。
    *   **核心组件接口**：定义 `EvaluationRequest`, `EvaluationResult`, `TraceEvent` 等核心数据结构（JSON Schema 示例）。
    *   **集成方式**：如何与现有 CI/CD 集成（如 GitHub Actions/GitLab CI 插件示例）。

#### 2. 明确“Ground Truth”的获取策略
*   **现状**：文档提到了 `expected_behavior` 和 `ground_truth`，但未说明在复杂 Agent 任务中，Ground Truth 是如何生成和维护的。
*   **建议**：
    *   **静态 Ground Truth**：适用于确定性任务（如计算器、SQL 生成），通过单元测试生成。
    *   **动态 Ground Truth**：适用于开放性任务，由专家标注，需定期更新。
    *   **自动 Ground Truth**：对于可验证状态的任务（如文件创建、数据库记录），通过状态检查自动生成 Ground Truth。

#### 3. 引入“成本效益分析”框架
*   **现状**：未提及评测本身的成本（人力、计算、时间）。
*   **建议**：增加“评测 ROI”章节，说明如何平衡评测覆盖率与成本。例如：
    *   **核心路径**：100% 自动化评测，高频运行。
    *   **边缘路径**：50% 自动化 + 50% 人工抽检，低频运行。
    *   **长尾路径**：仅人工评测，按需运行。

### 5. 架构层面反思

#### 1. 评测系统与生产系统的边界
*   **反思**：文档中评测系统似乎独立于生产系统，但在实际生产中，评测环境与生产环境的差异（Latency、Data Freshness、Model Version）可能导致评测结果失真。
*   **更优设计**：建议采用**Shadow Mode**（影子模式）或**Canary Evaluation**（金丝雀评测）。即在生产环境中，对部分真实流量进行“只读”评测，不返回结果给用户，仅记录日志用于分析。这能最大程度还原真实场景下的 Agent 表现。

#### 2. 反馈闭环的自动化程度
*   **反思**：文档描述了“归因并修复”的闭环，但人工干预环节较多。
*   **更优设计**：探索**自学习评测**（Self-Evolving Evaluation）。
    *   利用 LLM 自动分析 Bad Case，生成新的 Rubric 或 Prompt 优化建议。
    *   自动触发 A/B Test 验证优化效果。
    *   逐步将“人工定义 Rubric”转变为“LLM 辅助定义 + 人工审核”，降低人力成本。

#### 3. 多智能体（Multi-Agent）系统的评测复杂性
*   **反思**：文档主要聚焦于单 Agent 或线性任务流。但实际生产环境中，Agent 往往是多智能体协作（如 Planner + Coder + Reviewer）。
*   **更优设计**：
    *   **协作指标**：增加“Agent 间通信效率”、“冲突解决成功率”等指标。
    *   **责任分摊**：在多 Agent 系统中，单个 Agent 的错误可能被其他 Agent 掩盖。需要设计**责任追踪机制**（Responsibility Attribution），通过 Trace 中的因果链分析，定位是哪个 Agent 导致了最终失败。

#### 4. 可扩展性与插件化
*   **反思**：文档中评测能力较为固定。
*   **更优设计**：设计**插件化评测引擎**（Plugin-based Evaluation Engine）。
    *   **Rule Plugin**：基于规则的硬约束检查。
    *   **LLM Plugin**：基于 LLM 的软约束评估（如语气、专业性）。
    *   **Code Plugin**：基于代码的精确验证（如执行 Python 脚本检查输出格式）。
    *   允许业务方通过开发插件，自定义评测逻辑，而非由平台团队统一开发，提升系统灵活性。
