### 3. 其他问题清单

1.  **术语一致性 (Minor)**：
    *   文中混用了 `Skill` 和 `Tool`。在 Agent 架构中，`Tool` 通常指原子能力（API 调用），`Skill` 通常指复合能力（包含 Prompt + Tool 调用逻辑）。建议在全篇统一术语，或在首次出现时明确定义：*“本文中 Skill 指代封装了特定 Prompt 和 Tool 调用逻辑的模块化单元”*。
    *   `Trajectory` 与 `Trace` 混用。建议统一：`Trace` 为技术侧记录的原始日志流，`Trajectory` 为经过清洗后用于评测的逻辑执行路径。

2.  **缺乏失败模式的具体案例 (Minor)**：
    *   “二、指标与标准”中提到的“护栏指标”很好，但缺乏具体案例。例如：*“客服 Agent 若仅优化‘对话轮数’，可能导致‘敷衍式结束’。护栏指标应包含‘用户情绪负向词占比’或‘工单升级率’”*。增加此类反直觉案例能增强文档的警示作用。

3.  **自动化演进的风险评估不足 (Minor)**：
    *   “六、Case 挖掘... 4. 自动演进的边界”提到了人工审查，但未提及**灰度发布（Canary Release）**的具体比例建议。建议补充：*“自动生成的 Prompt 变更，必须经过 1% -> 5% -> 100% 的流量灰度，且每阶段监控核心护栏指标无劣化后方可全量。”*

4.  **性能开销未提及 (Minor)**：
    *   可观测性（Trace、Log）和 LLM as Judge 都会带来额外的 Token 消耗和延迟。文档未提及**采样率（Sampling Rate）**策略。建议补充：*“在非故障时段，建议将全量 Trace 采样率设为 10%-20%，全量记录用户反馈关联的请求。”* 以平衡成本与覆盖率。

### 4. 改进建议

#### 1. 增强“可执行性”：增加代码/配置模板
目前的文档偏向方法论。建议在每个章节末尾增加一个“最小可行示例（MVE）”折叠块。

**示例：Rubric YAML 模板**
```yaml
# rubrics/recommendation_budget_v1.yaml
id: recommendation_budget_v1
description: 检查商品推荐是否满足预算和品牌约束
checks:
  - id: budget_check
    type: rule_based
    logic: "all(item.price <= 8000 for item in result.items)"
    severity: blocker  # 阻断发布
  - id: brand_check
    type: rule_based
    logic: "not any('apple' in item.brand.lower() for item in result.items)"
    severity: warning  # 仅告警
  - id: evidence_check
    type: llm_judge
    prompt: "检查回复中提到的参数是否有对应的检索来源支持..."
    threshold: 0.9
```

#### 2. 明确“离线”与“在线”的数据同步机制
在“三、评测资产”和“六、Case 挖掘”之间，缺少数据流动的机制说明。
**建议补充**：
*   **Bad Case 入库流程**：线上监控发现异常 -> 自动提取 Context & Trace -> 脱敏 -> 存入 `eval_dataset/bad_cases/` -> 触发离线回归测试 -> 通过后合并至主分支评测集。
*   **版本对齐**：确保线上 Agent 使用的 `Prompt Version` 与离线评测使用的 `Prompt Version` 严格一致。建议在 CI/CD 流水线中增加“Prompt 哈希校验”步骤。

#### 3. 细化“LLM as Judge”的偏差校正
在“二、指标与标准”中，提到 LLM Judge 有偏差。
**建议补充**：
*   **Self-Consistency**：对同一输出调用 Judge 模型 3-5 次，取多数投票结果，减少随机性。
*   **Chain-of-Thought (CoT)**：要求 Judge 模型先输出推理过程，再输出分数，提高可解释性和准确性。
*   **Reference-based vs Non-reference-based**：明确在什么场景下需要人工标注的 Ground Truth 作为参考，什么场景下可以无参考评判。

#### 4. 增加“成本监控”维度
Agent 的核心痛点之一是 Token 成本。
**建议在“五、在线评测”指标中增加**：
*   `Token Cost per Task`：单任务平均 Token 消耗。
*   `Cost Efficiency Ratio`：(Task Success Rate) / (Token Cost)。
*   **告警策略**：当某次 Prompt 修改导致成本上升 20% 但成功率仅上升 1% 时，触发人工审查。

### 5. 架构层面反思

#### 1. 从“功能模块”到“数据管道”的思维转变
文档目前的结构是按“模块”（离线、在线、Case、观测）划分的。但在生产架构中，Agent 评测本质上是一个**数据管道（Data Pipeline）**：
`Raw Traffic -> Ingestion (脱敏/采样) -> Storage (Trace/Cases) -> Processing (LLM Judge/Rule Engine) -> Analytics (Metrics/Dashboard) -> Feedback (Auto-fix/Regression)`

**建议**：在文档开头增加一个**架构拓扑图（Architecture Topology）**，展示数据流向，而不仅仅是功能模块图。这有助于工程师理解各组件的依赖关系（例如：观测基建是评测的前提，评测是归因的前提，归因是优化的前提）。

#### 2. 解耦“评测逻辑”与“Agent 运行时”
文档中隐含了评测逻辑可能嵌入 Agent 运行时的风险。
**反思**：
*   **Bad Design**: 在 Agent 代码中直接调用 Judge 逻辑（如 `if (judge.score < 0.5) retry()`）。这会导致运行时延迟增加，且 Judge 失败会阻塞主流程。
*   **Good Design (建议强调)**：**旁路观测（Side-car Pattern）**。Agent 负责执行，Trace 异步写入存储。评测系统独立消费 Trace 数据。只有当评测结果作为“实时护栏”（Real-time Guardrail）介入时，才允许同步调用，且必须有超时兜底（Fail-open 或 Fail-closed 策略需明确）。

#### 3. 评测体系的“自反馈”闭环
文档提到了“评测体系迭代闭环”，但未强调**评测数据的闭环**。
**建议**：
*   建立**评测元数据（Meta-Evaluation）**。即：记录“Judge 模型对某个 Case 的判断”与“人工专家最终判断”的一致率。
*   如果一致率低于阈值（如 85%），自动触发“Rubric 修订工单”或“Judge 模型微调/替换”流程。
*   这构成了文档中提到的“两条闭环”中更深层的一条：**对评测者本身的评测**。这是从 P7 迈向 P8 的关键区别——不仅构建系统，还要构建“构建系统的系统”。
