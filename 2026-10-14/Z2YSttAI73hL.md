### 3. 其他问题清单

1.  **依赖不可控（严重）**
    *   **技术依据**：生产级代码或配置严禁直接依赖未经审计的外部第三方资源。`du-mozzie` 并非当前项目所有者或可信组织。
    *   **影响**：一旦该 GitHub 仓库被 Fork、改名、删除或所有者更改权限，文档中的图片将永久失效（Broken Link）。这在长期维护的技术文档中是不可接受的。

2.  **安全边界缺失（严重）**
    *   **技术依据**：AI Agent 的 Context 文件通常会被直接喂给 LLM。如果图片内容被恶意篡改（例如替换为包含“忽略之前所有指令”的文本的图片，或通过 OCR 提取的恶意 Prompt），将构成典型的**间接提示词注入（Indirect Prompt Injection）**攻击向量。
    *   **影响**：导致 AI Agent 行为异常、泄露敏感数据或执行非法操作。

3.  **缺乏版本管理意识（一般）**
    *   **技术依据**：Markdown 中的外部资源没有像 `package.json` 或 `go.mod` 那样的版本锁定机制。
    *   **影响**：无法追踪图片变更历史，无法进行 Code Review 时对图片变更进行有效审查。

### 高级策略：围绕一个业务问题设计独特机制（不要背名词）

**推荐问题**：*"在有限上下文窗口中，如何既保留稳定的用户偏好，又适应用户临时变化，同时避免压缩后丢失关键细节？"* —— 用户画像（分层+4C 判定升级）→ 分层上下文组织 → 动态编排决定本轮放什么 → 差异化压缩解决窗口不足 → 细节召回找回丢失内容；冲突时先召回判断是长期变化/场景差异/临时兴趣，无法确定则向用户澄清而不是覆盖画像。

#### 方案 B：若必须使用外链（不推荐，需严格管控）
如果图片必须来自外部（如 CDN），需满足以下条件：
1.  **使用公司统一 CDN**，而非个人 GitHub Raw 链接。
2.  **内容哈希校验**：在文档元数据或 CI 流程中校验图片的 MD5/SHA256，确保内容未被篡改。
3.  **安全扫描**：CI 管道中集成图片安全扫描，检测是否包含敏感信息或恶意 Payload。

### 5. 架构层面反思

*   **上下文工程的原子性**：
    AI Agent 的 Context 文件不应是简单的“文档”，而应是**结构化、可验证、安全隔离**的数据资产。引入外部非可信资源破坏了上下文的**封闭性（Closed World Assumption）**。
*   **可观测性与可审计性**：
    在生产环境中，每一次 Context 的变化（包括图片）都应被记录在案。使用外部链接使得“上下文快照”无法完整复现，导致故障排查时无法还原当时的输入状态，违反了**可重现性（Reproducibility）**原则。
*   **演进建议**：
    建议建立内部的技术文档图片规范：
    1.  所有图片必须本地化存储或通过公司认证 CDN 分发。
    2.  所有图片必须配有语义化的 Alt 文本，以便 LLM 进行多模态理解或纯文本降级处理。
    3.  在 CI 中添加 Markdown 链接检查（Link Checker），拦截失效外链和外部非白名单链接。
